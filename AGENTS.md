# AGENTS.md — PoKingHill (UU_AGENT)

Standing directives for any coding agent working in this repo. Project-specific anchors are in *italics*.

## 1. Workflow, Tooling & Asset Pipeline

- **Git & Docs:** Work on `master` only. Stage and commit pending changes before any sync (pull, rebase, push). Check `/DOCS` first.
  *Here: `DOCS/tasks.md` (build checklist and contract), `DOCS/rl_optimization_log.md` (run log and decisions), `DOCS/training_report.html` and `training/STAGED_TRAINING.md` (what to train next).*
  Display the deployment build version `YYMMDD` in the bottom-right corner, generated by an automated build script from the current date or the Git commit date.
- **Automation & headless:** Drive scene, prefab and level setup via CLI. Use headless Blender or Blender MCP; when modifying a Blender scene, archive the original `.blend` in the raw asset path and export a GLB copy to the export asset path.
  *Here: Unity batch mode does not work (no headless licence): drive the open editor with the Unity CLI (`$LOCALAPPDATA/Unity/bin/unity.exe`), or launch a normal editor with `-executeMethod … -kothExit`. Kim's source scan is `Assets/Art/Raw/Kim/Kim.glb` (read by `tools/make_kim.py`); Blender-generated assets land in `Assets/PoKingHill/{Fighters,Maps}`. Blender is not installed on every machine.*
- **UI documentation:** Save every UI change as an HTML report with annotated before/after screenshots in `SCREENSHOTS/`.
  *Here: `SCREENSHOTS/archive/` holds earlier captures and the TensorBoard report images; each UI report gets its own folder (e.g. `SCREENSHOTS/ui-261017/`).*

## 2. Training Lifecycle & Resource Management

- **Headless execution:** Close the editor for pure RL, runs over 30 min, or to reclaim memory. Keep simulation UIs visible otherwise.
- **Pruning & cleanup:** Delete abandoned run directories, scratch checkpoints and logs with fewer than 5,000 steps.
  *Here: `training/scripts/prune_runs.py [--apply]` and `tools/cleanup_unused.sh [--apply]`.*
- **Telemetry:** Stream kinematics, actions, observations and metrics (win/loss) locally or to Azure Table Storage.
  *Here: `MatchLog` JSONL + Elo ladder in `persistentDataPath`; `ObsRecorder` / `RunObsDump` for observations; TensorBoard under `training/runs/`, started when training launches.*

## 3. Physics, Collisions & Verification Gates

- **Collision rules:** Primitive colliders only (capsules, spheres, boxes); never raw bones or visual meshes. Enable self-collision on every non-adjacent pair (all but direct parent-child). Ensure zero mesh penetration across rest pose, T-pose and joint limits (swing arcs).
  *Here: `training/scripts/collision_audit.py` → `SCREENSHOTS/collision-<YYMMDD>/report.html`.*
- **Physical fidelity:** Gravity −9.81 m/s², anatomical mass, realistic joint and torque limits.
- **Mesh & rig pipeline:** Validate skinned meshes and extract rig hierarchies before training.
- **Graduation gate:** Export an ONNX policy only when mean reward meets the target for 100 consecutive episodes with zero NaN gradients.
  *Here: a checkpoint is trusted only after its Unity gate too (trajectory parity or statistical parity, see CLAUDE.md).*
- **HTML milestones:** For runs over 30 min, write an HTML report with a 3-tier milestone breakdown (Toddler, Child, Adult), top-3 metric charts and run-over-run deltas.
  *Here: `training/scripts/make_report.py`.*

## 4. Output Directives

- **Strategic direction:** If a code change exceeds 100 lines and the prompt has no pending questions, offer 3 architecture/roadmap questions.
- **TL;DR:** Append a ~20-word TL;DR to responses exceeding 100 words.
- **Biggest problem:** At the end of every response, suggest a solution for the biggest problem in the app and ask whether to go ahead with it or do something else.

## CI/CD and Azure (same section in every Po repo)

- A push to the default branch builds WebGL and deploys it to the game's Azure Static Web App (`.github/workflows/webgl.yml`). It runs on the self-hosted `unity` runner on the dev PC, one Unity build at a time across all games, so the PC must be on. `tools/deploy_webgl.ps1` stays for a manual deploy, but CI is the normal path.
- The workflow has no `pull_request` trigger, on purpose: the repo is public and the runner is a real PC. Never add one.
- Tests pass on any machine: no drive-letter, temp-folder or working-directory assumptions, and no live config value hard-coded as an expected result (read it from the same config the app reads).
- A red run on the default branch gets an ntfy push from the CI watcher in PoPunkouterSoftware. Fix it, or say why it is red.
