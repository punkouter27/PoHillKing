# AGENTS.md — PoHillKing

PoHillKing (Unity project name PoKingHill): king of the hill between physics-simulated human bodies, MuJoCo in Unity
and in training. This file is the repo's standard and its working notes; `CLAUDE.md` only points here. Three parts:
**1. Coding standard** (the Po game standard, how this repo meets it, house rules, working notes), **2. Concurrent work**
(several agents or people on one machine), **3. Verify the repo** (the exact commands, in order).

# 1. Coding standard

## 1.1 Po Game Standard (Unity / Unreal RL games)

This repo is one of several independent Po games. It follows the conventions below, but it owns every file:
nothing is generated from, synced with, or required to stay identical to another repository (no "same file in
every game" headers, no sync scripts that copy into other repos). Third-party code it needs (ML-Agents, MuJoCo
plugins, URLab) is vendored INSIDE this repo at a pinned version. Azure resources may be shared through `PoShared`.

### Repo skeleton
```
README.md   AGENTS.md (this standard + repo notes)   CLAUDE.md ("Read AGENTS.md.")
docs/       lowercase, all prose (no DOCS/, no root DESIGN.md/SPEC.md/tasks.md — move them into docs/)
scripts/    build/publish/helper scripts (Unity: Tools/ is renamed scripts/ unless Unity itself needs it)
.github/workflows/<one file>.yml   the ONLY workflow
pyproject.toml with a [tool.ruff] section for any Python in the repo
```
No absolute local paths (C:\Users\...) committed anywhere. No build outputs or node_modules tracked.

### Web page around the game (WebGL template / web viewer)
- The page chrome is drawn ONCE, by the HTML page, OUTSIDE the game canvas, so it can never overlap the HUD:
  a 44px top bar (game name top-left, settings gear / fullscreen top-right) and the version `vYYMMDD` bottom-right
  in the bar's counterpart or a 20px footer strip. The canvas fills the remaining viewport.
- The in-game HUD does NOT repeat the game name or version (it may show them inside menus, not as corner chrome).
- Same tokens as the web apps: dark background `#0b0f17`, surface `#121826`, text `#e6e9f2`, muted `#9aa3b5`,
  accent `#6366f1`, Inter/system-ui font. Text ≥ 4.5:1 contrast.

### Orientation (C11)
The canvas fills any viewport (no fixed portrait aspect, no pillarboxing). UI is anchored and DPI-scaled
(Unity: CanvasScaler "Scale With Screen Size" or UI Toolkit PanelSettings scale-with-screen; Unreal: UMG anchors +
DPI curve). Must be checked at 1600x900 (landscape) and 450x800 (portrait) — screenshots in the PR/commit notes.

### Version
One stamp, UTC `yyMMdd`, computed once by the publish/build script and injected into: index.html, diag.html,
and the player (`PlayerSettings.bundleVersion` / Unreal ProjectVersion) so `Application.version` matches the page.

### /diag (games)
`/diag` (static `diag.html` generated by the publish script) titled **System status**, same layout as the web apps:
overall banner, then **API / Data / Services** sections. It must LIVE-probe (fetch from the browser, with latency)
every external dependency the game really calls (leaderboard tables/functions, weather APIs, AI APIs, replay bundles,
model files), plus the WebGL2 capability and that the build bundle files exist. Nothing hard-coded as "Ready".
The checks are listed in the repo's own config (e.g. `scripts/webgl.json` → `diagChecks`).

### In-game diagnostics overlay (C12)
`Tab` (and a 44px corner button on touch devices) toggles an overlay showing: FPS, current episode reward,
inference latency (ms, rolling average), curriculum stage. Readable text (≥ 4.5:1 on an opaque panel).

### Demo mode (C13)
After 30 s with no input (keyboard, mouse, touch, gamepad) from load or from last input: hide non-essential HUD,
all agents are driven by the trained policy (inference only), showcase cameras cycle (~6–8 s each); any input
returns control and the HUD. Idle threshold, camera list and dwell time are editor-tunable assets.

### Rewards + editor-first config (C9, C10)
Reward includes penalties for joint torque², joint angular velocity², action rate ‖a_t − a_{t−1}‖², and foot sliding
(foot planar speed while in contact), each with its own weight. Reward weights, curriculum thresholds, cameras and UI
references live in ScriptableObjects / `[SerializeField]` (Unity) or DataAssets / `UPROPERTY(EditAnywhere,
BlueprintReadWrite)` (Unreal); Python trainers read the same values from the repo's training config. Changing a
penalty does not retrain shipped policies — note this in docs when shipped models predate the change.

### Workflow
- Unity: the WebGL player is built locally with the EXACT pinned editor (Unity cannot be licensed in CI) by
  `scripts/publish_webgl.ps1`, which runs EditMode tests first, then builds, zips and publishes a `webgl-*` release.
  The one workflow: on release → deploy to the game's Static Web App → check the live page AND /diag; on push →
  Python checks (`ruff check`, `ruff format --check`, `pytest`) only.
- Unreal: the one workflow builds and deploys the repo's web front (viewer / showcase + /diag) to its Static Web App,
  after Python checks. The Unreal project must compile from a fresh clone (all plugins vendored in `Plugins/`).

### Tests
Python: real pytest tests (collected by pytest, not ad-hoc scripts), ruff clean. Unity: EditMode tests pass before
every publish. Tests never write into tracked files.

## 1.3 House rules

### 1.3.1 Workflow, Tooling & Asset Pipeline

- **Git & Docs:** Work on `master` only. Stage and commit pending changes before any sync (pull, rebase, push). Check `docs/` first.
  *Here: `docs/tasks.md` (build checklist and contract), `docs/rl_optimization_log.md` (run log and decisions), `docs/training_report.html` and `Training/STAGED_TRAINING.md` (what to train next).*
  The build version `vYYMMDD` (UTC) is computed once by `scripts/publish_webgl.ps1` and shown by the web page's footer, `/diag` and `Application.version` (section 1.2).
- **Policy impact before changes:** Before changing code, state which policies are affected: body physics affects that body's policies; rules affect policies acting under them; a new skill affects its policy and director transition rows; visuals affect none. Record the impact and intended regression scenarios in `docs/<YYYYMMDD>/`.
  *Here: also keep `docs/rl_optimization_log.md` as the chronological training and parity record.*
- **Automation & headless:** Drive scene, prefab and level setup via CLI. Use headless Blender or Blender MCP; when modifying a Blender scene, archive the original `.blend` in the raw asset path and export a GLB copy to the export asset path.
  *Here: batch mode works with the pinned editor 6000.6.9f1 (EditMode tests and the WebGL build run headless from `scripts/publish_webgl.ps1`); gates that need a rendering editor still launch a normal editor with `-executeMethod … -kothExit` or drive the open editor with the Unity CLI (`$LOCALAPPDATA/Unity/bin/unity.exe`). Kim's source scan is `Assets/Art/Raw/Kim/Kim.glb` (read by `scripts/make_kim.py`); Blender-generated assets land in `Assets/_Project/{Fighters,Maps}`. Blender is not installed on every machine.*
- **UI documentation:** Save every UI change as an HTML report with annotated before/after screenshots in `SCREENSHOTS/`.
  *Here: `SCREENSHOTS/archive/` holds earlier captures and the TensorBoard report images; each UI report gets its own folder `SCREENSHOTS/ui-<YYMMDD>-<feature>/` (`index.html` before | after per screen + one annotated `side-by-side.png`), written by `scripts/screenshots.py` (section 3).*

### 1.3.2 Training Lifecycle & Resource Management

- **Headless execution:** Close the editor for pure RL, runs over 30 min, or to reclaim memory. Keep simulation UIs visible otherwise.
- **Pruning & cleanup:** Delete abandoned run directories, scratch checkpoints and logs with fewer than 5,000 steps.
  *Here: `Training/scripts/prune_runs.py [--apply]` and `scripts/cleanup_unused.sh [--apply]`.*
- **Telemetry:** Stream kinematics, actions, observations and metrics (win/loss) locally or to Azure Table Storage.
  *Here: `MatchLog` JSONL + Elo ladder in `persistentDataPath`; `ObsRecorder` / `RunObsDump` for observations; TensorBoard under `Training/runs/`, started when training launches.*
- **Logs in `docs/`:** Log training metrics, decisions and updates to `docs/` so later agents can track progress.
  *Here: save dated change notes and training progress under `docs/<YYYYMMDD>/`, and append every run, measurement or decision to `docs/rl_optimization_log.md` (newest last).*
- **Progress updates:** Estimate training time at startup, then send hourly updates: a status grid (run, iteration, key metrics), key improvements and a short summary.
  *Here: queue scripts write timestamped lines to `Training/runs/overnight/progress_*.txt` (`queue_hill.note`); the ETA and the hourly grid are the agent's job until a script prints them.*
- **Resource limits:** Save and commit before long training runs. Close Unity for runs over 30 minutes or when free RAM is below 4 GB. Never delete a run written in the last 24 hours or one a queue may resume.
  *Here: one 4096-environment run at a time; follow the queue/checkpoint state before pruning anything.*

### 1.3.3 Physics, Collisions & Verification Gates

- **Collision rules:** Primitive colliders only (capsules, spheres, boxes); never raw bones or visual meshes. Enable self-collision on every non-adjacent pair (all but direct parent-child). Ensure zero mesh penetration across rest pose, T-pose and joint limits (swing arcs).
  *Here: `Training/scripts/collision_audit.py` → `SCREENSHOTS/collision-<YYMMDD>/report.html`.*
- **Physical fidelity:** Use Earth gravity (−9.81 m/s²), anatomical mass, realistic joint, torque and speed limits; validate skinned meshes and keep rig hierarchies aligned with simulator joints.
- **Action smoothing:** Promote human-like, fluid joint motion without jitter: torque/action-rate penalties, low-pass filtering of actions, or jerk minimisation in the reward.
  *Here: the `action_rate` reward term (`koth/env.py`, -0.03 in the hill recipe) and the action low-pass `smooth` (`koth/action_map.py` = `ActionMap.cs`, carried in the brain's `_action.json`, `train.py --action-smooth`). Too much smoothing stalls mirror duels (log 2026-10-29, `scripts/sweep_smooth.py`): judge it by decided share, not only by jitter.*
- **Model fidelity:** Keep rig hierarchies aligned with simulator joints.
  *Here: MuJoCo is the only simulator; regenerate imported Unity models from the Python MJCF source and pass `ModelDumpCheck`.*
- **Behaviour decomposition:** Split behaviours into a few small, separately trained ONNX policies (one per skill family: locomotion/fight, get-up, later kick or carry), never one giant do-everything network; steer each with command inputs (velocity, target, style) rather than adding a policy per variant. Every policy for a body shares the same observation layout, joint order and action map, so any of them can take over mid-motion. A rule-based director (state machine) above them picks the active policy from simulator state; policies never pick each other. Load and warm every policy at scene start and switch by changing which worker runs, never by loading a model mid-match. Keep the hand-over continuous (shared last action and clock) and train each policy from the states it inherits (get-up from real falls, fight from get-up endings) instead of blending two policies' outputs, which neither was trained on. Each switch rule is mirrored in the Python reference and gated like any other rule. Model size and RAM are not the limit (~1 MB per policy); the training cost of each new skill and the director's combinatorics are, so add a policy only when a command input cannot cover it.
  *Here: `PolicyRunner` holds the fight and get-up workers, `MatchDirector.OutWithGetUp` is the director, mirrored by `duel_stats.py --getup --hill-rule`. Unreal/URLab: the same split, with the director in C++ or Blueprints over NNE workers created at BeginPlay.*
- **Build so changes do not force retraining from scratch:** Treat each policy's interface (observation order, joint order, action map) as a frozen contract: only append new inputs at the end, never reorder or remove them; if the contract must break, distil the old policy into the new layout instead of starting RL from zero. Put presentation, HUD, match flow and director rules outside the policies, so changing them needs only a re-gate, not training. Expose tunable game values (arena size, sea, friction, push strength) to training as randomized ranges, so a change inside the range needs no retraining and one outside it needs a fine-tune. When a policy must change, fine-tune it from the shipped checkpoint (warm start, fresh critic warmed up first), keep earlier and easy opponents in the pool so it does not forget, and judge it against several of them before export. Before any game change, name which policies it touches and retrain only those: a body's physics touches every policy of that body; arena or win rules touch the fighters; a new skill touches only its new policy plus a director rule; looks and UI touch none. Log that decision in `docs/`.
  *Here: `train.py --warm` (zero-weight padding for appended inputs, action-scale folding), `--resume`, `--critic-warmup 10-20`, `scripts/onnx_to_ckpt.py` when `runs/` is gone, judged with `judge.sh` / `judge_hill.py`. Fighters are trained against the other bodies' frozen fighters: after one body's fighter changes, re-judge the others before retraining them.*
- **Graduation gate:** Export an ONNX policy only when its target score holds for 100 consecutive episodes with zero NaN gradients.
  *Here: a checkpoint is trusted only after its Unity gate too (trajectory parity or statistical parity, section 1.4).*
- **HTML milestones:** For runs over 30 min, write an HTML report with a 3-tier milestone breakdown (Toddler, Child, Adult), top-3 metric charts and run-over-run deltas.
  *Here: `Training/scripts/make_report.py`.*
- **Training telemetry:** Run TensorBoard with each training run, log metrics and progress, and estimate the run duration at startup.

### 1.3.4 Policy Architecture & Retraining

- **Skill hierarchy:** Prefer a small policy per motor-skill family (locomotion, balance/get-up, task skills), with command inputs for variants rather than a new policy for every variant. A layered, rule-based director should switch skills from physical state through one transition table mirrored in every runtime; policies must not select other policies.
  *Here: the current shipped runtime has per-body fighter and get-up brains. Preserve its Python/Unity parity; any move to shared skill policies or a transition table must update both sides and their gates together.*
- **Policy hand-overs:** Policies for a body must share observation layout, joint order, action map, timing and motion-style reward. Preload policies, pass the last action between them, avoid pose snaps or output blending, and train each policy on the states it inherits (including real falls for get-up).
- **Frozen interfaces:** Append observation inputs only at the end and zero-initialize their weights. Never reorder or remove existing inputs; if an interface break is unavoidable, distil the prior policy into the new layout.
- **Character independence:** Every new character gets its own training run and policies; do not reuse another character's brain, even for similar bodies. Train from scratch through every ladder level and gate against the existing roster. Personality comes from character traits and learned style-reward weights, not scripted director behavior. Once a character is trained, avoid fully retraining existing characters.
- **Checkpoint provenance and regression:** Tag every checkpoint with its observation/action interface and physics versions. After a change, rerun and record every affected policy's regression scenarios for both task performance and realism.

## 1.4 Working in this repo

### What this is

PoKingHill: king-of-the-hill between physics-simulated human bodies: Kim, a scanned 56 kg woman, Trump, a 102 kg man from a rigged GLB, and Grandpa, an 86 kg man rigged from an unrigged GLB (more custom rigged meshes to come). The Unitree G1 robot, the first body, left the game on 2026-10-20; its training code, checkpoints, ONNX brains and gates stay, the human recipes were built from it, and what it taught is in `Training/TRAINING_LESSONS.md`. Brains are trained in Python on MuJoCo Warp and run in Unity 6000.6.9f1 through the `org.mujoco` plugin and `com.unity.ai.inference` (Sentis' successor). **PhysX is never used**: Unity's physics mode is Script, every scene must have zero Collider/Rigidbody, and MuJoCo is the only simulator in both worlds.

`docs/tasks.md` is the build contract (phases 0, A-D, rung bars R0-R5). `docs/rl_optimization_log.md` is the chronological record of every run, measurement and decision, newest at the bottom. Read the bottom of it before changing training or parity tooling.

### Commands

Python (from `Training/`, uv project, Python 3.11, CUDA torch). The `.sh` scripts call `.venv/Scripts/python.exe` directly.

```bash
uv run python scripts/train.py --rung r0 --num-envs 4096 --iters 1500 [--resume ckpt.pt | --warm ckpt.pt] [--opponent a.pt b.pt:stand] [--reward self_edge=-5]
uv run python scripts/eval.py --rung r4league --ckpt runs/league/careful1.pt --opponent runs/league/gen3.pt --seeds 3 --num-envs 256
bash scripts/judge.sh <league checkpoint name>       # champion bars: vs standing walker, gens 3-7, champion, itself
uv run python scripts/export_policy.py --ckpt <ckpt.pt> --name attacker   # -> Assets/_Project/RL_Models/<name>_policy.onnx
```

### Architecture

**One model, two simulators.** `koth/build_mjcf.py` is the single source of the physics model: it writes the training MJCF, a `_unity.xml` variant stripped of what the plugin cannot import, `model_dump_<tag>.json` (the parity reference) and `joint_map.json` (canonical 29-joint order). The MuJoCo part of every Unity scene is *imported* from that XML by `ParityBatch`, never hand-built; the game scene around it is composed by hand (see Scenes). Change physics on the Python side and re-import; never edit imported MuJoCo components in Unity. Settings the plugin cannot import (`ls_iterations`, keyframes, contact pairs) are either avoided in the MJCF or written from C# after init.

**Control loop, mirrored on both sides.** 2 ms physics step, policy every 10th step (50 Hz). Observations: 103 locomotion inputs (`koth/obs.py:build_obs` = `ObsBuilder.cs`), plus 9 combat inputs for 112-dim brains (`build_combat` = `ObsBuilder.FillCombat`). The 3 command slots come from a geometric goal law (`obs.goal_command` = `GoalCommand.cs`), not from extra observations; training's `obs.tactic_goal` moves its goal point in the `r4tactic` rung (Unity's Tactician was cut on 2026-10-21). `ctrl = default + 0.5·action`, unless the brain carries `<name>_action.json` (tanh map, per-joint scale, torque window: `koth/action_map.py` = `ActionMap.cs`, read by `PolicyRunner` and `duel_stats.py`). Any change to one side of these pairs must be made on the other, then re-gated.

**Unity runtime** ([Assets/_Project/Core/Scripts](Assets/_Project/Core/Scripts), one folder per concern: `Brain/` the control loop mirrored in Python (obs, goal law, action map, `PolicyRunner`), `Match/` rules and state (director, events, settings, sea, sensors, telemetry), `Presentation/` cameras, effects, audio, looks, `Hud/` the UI (`HudView` split into partial files), `Diagnostics/` parity probes and the command line): everything hooks `MjScene` events (`postInitEvent`, `preUpdateEvent`, `postUpdateEvent`) and reads/writes `mjData` through unsafe pointers. No Instantiate/Destroy, no scene reloads: rounds reset by writing qpos/qvel. `PolicyRunner` must rewrite held ctrl in `preUpdateEvent` every step because `MjActuator.OnSyncState` zeroes ctrl after each `mj_step`. The physics tick is allocation-free; keep it that way.
- `MatchDirector`: the match state machine (`Menu → Fight → Result (→ Replay) → Fight | Menu`); quick match and custom (`FfaPlayers` = 8 at once, `FfaSeats`: every available (or ticked) agent once before any repeats, so with three brains it is 3 + 3 + 2; `StartFreeForAll(16)` seats the whole field, and `launchPlayers` = 16 only for `PerfProbe`), the 16-player bracket (`StartTournament`: single elimination of one-round 1v1 duels over the menu's seats, 01 v 02, 03 v 04 ..., 15 matches, `BuildBracket`; every duel names a winner on the spot: the last one in, else nearest the centre when time is up, else whoever went over last, else the higher Elo; no replays, so 15 duels always end with one champion), 4x4 heats; every agent is a brain (no human player). Seats agents (`roster`, class `Agent`: a brain and how it is driven) on bodies of their own kind (`bodies`, the `PolicyRunner`s: `g1`/`kim`/`trump`/`grandpa`), reorders `bodies[]` at every launch (cache your own copy if you index by body), parks unused bodies 50 m up, points each brain at one opponent (nearest, or with `Targeting.Opportunist` the one easiest to push off; brains were trained 1v1). The statistics gate (`statsRounds`) bypasses Result and the presentation.
- Shoves and jabs (`MatchDirector.Shoves.cs`, `GameSettings.Strikes`, on by default; Settings > Advanced): a fighter within `strikeReach` (0.85 m) of its target and facing it throws a scripted strike every 0.9-1.8 s (`PolicyRunner.BeginStrike`: both arms = shove, one = jab; the striking arm's shoulder pitch and elbow are laid over the brain's targets in `WriteCtrl` only, `Ctrl` is untouched). A fist reaching the target's torso while the arm goes out gives it `strikeImpulse` (42 N s, a jab 0.6 of it, x1.6 with Heavy) / its mass away from the striker, and the striker 0.3 of it back. Never in a statistics gate, so the brain gates measure the brains alone. The learned side is the env's `strike_push` reward (push_out while a hand, arm or foot touches someone) and `scripts/strike_pass.py`; `eval.py` reports `strike_touch`.
- Presentation never gets called by the director: it subscribes to `MatchEvents` (state, round start/end, knock-out and its credit, down/recovered, impact, footfall, splash, caption). `HudView` (UI Toolkit, styles in `UI/Hud.uss` with a six-step type scale, one 9:16 column, no scrolling; one row of avatar badges with a `VitalsBar`, knock-out feed, intro card, replay bar with a draggable playhead, tabs Play/Agents/Settings on a bottom sheet that swipes down to a peek pill and turns dense when it would not fit; every option sits on the Settings page in sections Match/Picture/Sound/Advanced; Picture is Quality plus one Cinematic switch (effects, camera cuts and shake, slow motion); Advanced → Developer tools shows the FPS pill (dodges `Screen.cutouts`) and the debug button, debug tabs Perf/View/Tools, where View holds the overlays, win odds and captions), `BroadcastCamera` (Cinemachine, the only camera; intro crane on a Splines path + per-fighter orbit), `ReplaySystem` (disables `MjScene`, replays qpos via `mj_kinematics`, restores the exact state), `MatchFx` (particles, decals, post punch, shockwave via the `ShockwaveFeature` renderer feature, lightning, danger light), `BodyLook` (team paint, overlays, and the `FX/Fighter.shader` surface: seat-colour rim that turns red at the edge, wear from contacts, wet after the sea, hit flash), `TimeWarp` (slow motion at the rim and hit stop: `Time.timeScale` only, never in gates or replays), `QualityTier` (Low/Medium/High/Auto presets on the camera and sun, frame-time telemetry), `WinOdds`, `Commentator` (offline caption templates), `MatchLog` (local telemetry JSONL + Elo `Ladder` with record, KOs, assists in `persistentDataPath`). Options live in `GameSettings` (PlayerPrefs); the defaults are the least cluttered game (no intro, auto replay or developer tools, so no captions or win odds either). - Sensors and mechanics, all inert in the statistics gates unless a gate asks: `ContactLedger` (pairwise pushing impulse from `mj_contactForce`, knock-out credit and assists), `Biometrics` (capture point vs the planted feet = balance, capture point vs the rim = edge, strain history).
