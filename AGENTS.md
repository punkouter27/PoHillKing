## 2. Training Lifecycle & Resource Management

- **Headless execution:** Close the editor for pure RL, runs over 30 min, or to reclaim memory. Keep simulation UIs visible otherwise.
- **Pruning & cleanup:** Delete abandoned run directories, scratch checkpoints and logs with fewer than 5,000 steps.
  *Here: `training/scripts/prune_runs.py [--apply]` and `tools/cleanup_unused.sh [--apply]`.*
- **Telemetry:** Stream kinematics, actions, observations and metrics (win/loss) locally or to Azure Table Storage.
  *Here: `MatchLog` JSONL + Elo ladder in `persistentDataPath`; `ObsRecorder` / `RunObsDump` for observations; TensorBoard under `training/runs/`, started when training launches.*
- **Logs in `/DOCS`:** Log training metrics, decisions and updates to `/DOCS` so later agents can track progress.
  *Here: append to the bottom of `DOCS/rl_optimization_log.md` (newest last), one entry per run, measurement or decision.*
- **Progress updates:** Estimate training time at startup, then send hourly updates: a status grid (run, iteration, key metrics), key improvements and a short summary.
  *Here: queue scripts write timestamped lines to `training/runs/overnight/progress_*.txt` (`queue_hill.note`); the ETA and the hourly grid are the agent's job until a script prints them.*

## 3. Physics, Collisions & Verification Gates

- **Collision rules:** Primitive colliders only (capsules, spheres, boxes); never raw bones or visual meshes. Enable self-collision on every non-adjacent pair (all but direct parent-child). Ensure zero mesh penetration across rest pose, T-pose and joint limits (swing arcs).
  *Here: `training/scripts/collision_audit.py` → `SCREENSHOTS/collision-<YYMMDD>/report.html`.*
- **Physical fidelity:** Gravity −9.81 m/s², anatomical mass, realistic joint and torque limits.
- **Mesh & rig pipeline:** Validate skinned meshes and extract rig hierarchies before training.
- **Action smoothing:** Promote human-like, fluid joint motion without jitter: torque/action-rate penalties, low-pass filtering of actions, or jerk minimisation in the reward.
  *Here: the `action_rate` reward term (`koth/env.py`, -0.03 in the hill recipe) and the action low-pass `smooth` (`koth/action_map.py` = `ActionMap.cs`, carried in the brain's `_action.json`, `train.py --action-smooth`). Too much smoothing stalls mirror duels (log 2026-10-29, `scripts/sweep_smooth.py`): judge it by decided share, not only by jitter.*
- **Behaviour decomposition:** Split behaviours into a few small, separately trained ONNX policies (one per skill family: locomotion/fight, get-up, later kick or carry), never one giant do-everything network; steer each with command inputs (velocity, target, style) rather than adding a policy per variant. Every policy for a body shares the same observation layout, joint order and action map, so any of them can take over mid-motion. A rule-based director (state machine) above them picks the active policy from simulator state; policies never pick each other. Load and warm every policy at scene start and switch by changing which worker runs, never by loading a model mid-match. Keep the hand-over continuous (shared last action and clock) and train each policy from the states it inherits (get-up from real falls, fight from get-up endings) instead of blending two policies' outputs, which neither was trained on. Each switch rule is mirrored in the Python reference and gated like any other rule. Model size and RAM are not the limit (~1 MB per policy); the training cost of each new skill and the director's combinatorics are, so add a policy only when a command input cannot cover it.
  *Here: `PolicyRunner` holds the fight and get-up workers, `MatchDirector.OutWithGetUp` is the director, mirrored by `duel_stats.py --getup --hill-rule`. Unreal/URLab: the same split, with the director in C++ or Blueprints over NNE workers created at BeginPlay.*
- **Build so changes do not force retraining from scratch:** Treat each policy's interface (observation order, joint order, action map) as a frozen contract: only append new inputs at the end, never reorder or remove them; if the contract must break, distil the old policy into the new layout instead of starting RL from zero. Put presentation, HUD, match flow and director rules outside the policies, so changing them needs only a re-gate, not training. Expose tunable game values (arena size, sea, friction, push strength) to training as randomized ranges, so a change inside the range needs no retraining and one outside it needs a fine-tune. When a policy must change, fine-tune it from the shipped checkpoint (warm start, fresh critic warmed up first), keep earlier and easy opponents in the pool so it does not forget, and judge it against several of them before export. Before any game change, name which policies it touches and retrain only those: a body's physics touches every policy of that body; arena or win rules touch the fighters; a new skill touches only its new policy plus a director rule; looks and UI touch none. Log that decision in `/DOCS`.
  *Here: `train.py --warm` (zero-weight padding for appended inputs, action-scale folding), `--resume`, `--critic-warmup 10-20`, `scripts/onnx_to_ckpt.py` when `runs/` is gone, judged with `judge.sh` / `judge_hill.py`. Fighters are trained against the other bodies' frozen fighters: after one body's fighter changes, re-judge the others before retraining them.*
- **Graduation gate:** Export an ONNX policy only when mean reward meets the target for 100 consecutive episodes with zero NaN gradients.
  *Here: a checkpoint is trusted only after its Unity gate too (trajectory parity or statistical parity, see CLAUDE.md).*
- **HTML milestones:** For runs over 30 min, write an HTML report with a 3-tier milestone breakdown (Toddler, Child, Adult), top-3 metric charts and run-over-run deltas.
  *Here: `training/scripts/make_report.py`.*

## CI/CD and Azure (same section in every Po repo)

- A push to the default branch builds WebGL and deploys it to the game's Azure Static Web App (`.github/workflows/webgl.yml`). It runs on the self-hosted `unity` runner on the dev PC, one Unity build at a time across all games, so the PC must be on. `tools/deploy_webgl.ps1` stays for a manual deploy, but CI is the normal path.
- The workflow has no `pull_request` trigger, on purpose: the repo is public and the runner is a real PC. Never add one.
- Tests pass on any machine: no drive-letter, temp-folder or working-directory assumptions, and no live config value hard-coded as an expected result (read it from the same config the app reads).
- A red run on the default branch gets an ntfy push from the CI watcher in PoPunkouterSoftware. Fix it, or say why it is red.
